# 代码重构（code-refactor）

## 设计背景

重构是风险最高的代码操作之一——改好了没人注意，改坏了线上事故。
AI 面临的核心难题：用户对"好的架构"的标准是经验性的，
什么时候该抽、什么时候不抽、抽到什么程度，在不同项目、不同模块中答案都不同。

本 skill 的策略不是让 AI 独立判断——而是**提出多种方案让用户选择**，
同时深度依赖 experience-repo 中的用户偏好记录。

---

## 职责边界

### ✅ 本 skill 负责

- 拆分过大的文件/函数
- 抽取重复代码为公共方法
- 重新组织文件结构（合并/拆分文件）
- 改善模块间的耦合关系
- 统一不一致的命名/风格
- 清理不再使用的代码

### ❌ 本 skill 不负责

- 修改业务逻辑或行为（那是 logic-dev / quick-fix 的事）
- 新增功能（那是 logic-dev / ui-dev）
- 优化性能（除非性能数据和可维护性同时需要改善）
- 纯粹的风格格式化（如缩进、换行）

### ⚠️ 关键红线

```
重构 = 改结构不改行为
```

如果结构改动会导致行为变化，必须先告知用户并获得明确同意。

## 执行流程

### 阶段 1：调研（调用 research）

必须理解：
- 当前代码的痛点是什么（为什么需要重构）
- 有哪些调用方依赖当前接口（改了会影响谁）
- 当前模块的编码习惯（module-style）

### 阶段 2：加载经验库

重构极度依赖 experience-repo。加载经验库后，特别关注：
- `abstraction.md`——用户对"何时抽取"的偏好
- `cross-cutting.md`——用户对切面组织的偏好
- `interface-design.md`——用户对接口设计的偏好

如果没有这些分类的经验记录，在方案中标注"缺少偏好参考，按默认原则处理"。

### 阶段 3：分析痛点

向用户确认重构的目标（多选）：

```
当前代码的主要痛点是什么？
- [ ] 函数太长，难以理解
- [ ] 耦合太紧，改一处动全身
- [ ] 职责不分，什么都混在一起
- [ ] 文件太大，找不到东西
- [ ] 重复代码太多
- [ ] 拓展性差，新需求改不动
- [ ] 其他：...
```

### 阶段 4：提出多方案（核心步骤）

根据痛点，提出 **2-3 种方案**，覆盖保守→激进的光谱：

```
## 🔄 重构方案

### 方案 A：{保守方案名}
**改动范围**：{最小改动}
**做法**：{具体做法 3-5 步}
**收益**：{解决什么痛点}
**代价**：{引入什么变化}
**适合**：{什么时候选这个}

### 方案 B：{折中方案名}（推荐）
**改动范围**：{适中改动}
**做法**：{具体做法 3-5 步}
**收益**：{解决什么痛点}
**代价**：{引入什么变化}
**适合**：{什么时候选这个}

### 方案 C：{激进方案名}
**改动范围**：{较大改动}
**做法**：{具体做法 3-5 步}
**收益**：{解决什么痛点}
**代价**：{引入什么变化}
**适合**：{什么时候选这个}
```

每种方案说明：
- **改了哪些文件**（新增/修改/删除/合并/拆分）
- **调用方影响**（哪些文件要同步改接口调用）
- **和 experience-repo 中的经验是否一致**（如果冲突，标注出来）

### 阶段 5：用户选择 + 实现

用户选择方案后（或受启发给出新方向后），进入实现：

1. 按 plan-output 模板输出详细实施计划
2. 用户确认 → 开始重构
3. 每改一个文件，验证调用方是否需要同步更新

### 阶段 6：验证（调用 change-review + 额外检查）

重构特有的额外检查：

- [ ] 所有原有调用方是否仍然能正常工作
- [ ] 函数签名变更是否全部同步
- [ ] 是否需要保留旧接口做兼容过渡（deprecated wrapper）
- [ ] 文件拆分/合并后 require 路径是否正确

### 阶段 7：记录经验

重构过程中如果发现了新的偏好模式（如"这个模块的切面划分得很好，以后可以参考"），
建议用户记录到 experience-repo。

## 重构反模式（必须避免）

### ❌ 反模式 1：为了"干净"而过度拆分

```lua
-- 原来一个 30 行的函数
function M:ProcessData(data)
    -- 30 行逻辑
end

-- ❌ 拆成 10 个 3 行的函数——维护者要在 10 个函数间跳来跳去
function M:_Step1_Validate(data) ... end
function M:_Step2_Normalize(data) ... end
function M:_Step3_Transform(data) ... end
-- ... 7 more
```

**何时可以拆分**：被 ≥2 个调用方独立使用，或者拆出来的函数 ≥15 行。
10 个 3 行函数比 1 个 30 行函数更难维护。

### ❌ 反模式 2：为了"解耦"而引入过度抽象

```lua
-- ❌ 就一个调用方，却引入了接口层 + 实现层
local IDataHandler = {}
function IDataHandler:Process(data) end  -- 接口
local DataHandlerImpl = setmetatable({}, {__index = IDataHandler})
function DataHandlerImpl:Process(data) ... end  -- 实现
```

**何时可以加抽象层**：当确实需要多态（≥2 种实现）或需要 mock 测试时。
如果你的经验中有关于抽象的偏好，参考 experience-repo。

### ❌ 反模式 3：重构时顺手"修一下"

```
❌ "我在重构时顺便修了那个小 bug"
```

重构和修 bug 必须分开——合在一起会让 code review 无法区分
"结构变化"和"行为变化"。如果发现了 bug，先记下来，
用 quick-fix 单独修，或者在重构完成后再修。

---

## 关键原则

1. **重构 ≠ 重写**——行为不变是底线
2. **多方案而非单方案**——2-3 种方案让用户选，比 AI 自己定要好
3. **经验库是重构的罗盘**——用户对"好架构"的偏好记录在哪里，就往哪里走
4. **调用方影响必须明确**——改了签名就要改所有调用方
5. **不过度抽象、不过度拆分**——经验库中的"如非必要勿增实体"是默认原则

## 与其他 Skill 的关系

| Skill | 调用阶段 | 用途 |
|-------|---------|------|
| research | 阶段 1 | 理解现状、找调用方 |
| experience-repo | 阶段 2 + 全程 | **核心依赖**——用户的架构偏好 |
| module-style | 阶段 1 | 提取模块当前风格 |
| plan-output | 阶段 5 | 输出详细实施计划 |
| change-review | 阶段 6 | 审查 diff + 重构特有检查 |
| quick-fix | — | 重构中发现的 bug 用 quick-fix 单独修 |

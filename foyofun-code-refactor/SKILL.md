# 代码重构（foyofun-code-refactor）

## 设计背景

重构是风险最高的代码操作——改好了没人注意，改坏了线上事故。AI 的核心短板：
"什么时候该抽、抽到什么程度"的标准是经验性的，因人、因项目而异。
本 skill 的策略：**多方案让用户选** + **经验库当罗盘**，不让 AI 独断。

## 职责边界

✅ 负责：拆分过大文件/函数、抽取重复为公共方法、重组文件结构、
改善耦合、统一不一致风格、清理死代码、为接下来的业务需求调整结构。

❌ 不负责：修改业务行为（那是 logic/ui 的开发任务）、纯性能优化
（除非与可维护性同时需要）、纯格式化。

⚠️ 红线：**重构 = 改结构不改行为**。结构改动会导致行为变化时，
先停下来告知用户，获得明确同意才继续。

## 执行流程

### 阶段 1：调研（foyofun-code-research，强制）

必须摸清：当前痛点、**所有调用方**（改签名的影响面）、模块既成风格（foyofun-code-style）。

### 阶段 2：加载经验库（foyofun-code-experience）

重构极度依赖用户偏好，重点分类：abstraction（何时抽取）、cross-cutting（切面组织）、
interface-design（接口设计）。缺相关记录时在方案中标注
"缺少偏好参考，按默认原则处理"，并建议用户事后沉淀。

### 阶段 3：确认痛点

向用户确认重构目标（多选）：函数太长 / 耦合太紧 / 职责混杂 / 文件太大 /
重复太多 / 拓展性差 / 为即将到来的某需求铺路。**铺路型重构要求用户说清是什么需求**——
目标决定方案方向。

### 阶段 4：提出多方案（核心步骤）

按保守→激进光谱提出 **2-3 种方案**，每种写清：
改动范围（文件清单）、做法（3-5 步）、收益（解决哪个痛点）、
代价（引入什么变化）、调用方影响（谁要同步改）、
与经验库的冲突点（有则标注）。

### 阶段 5：Plan + 实现

用户选定（或受启发给新方向）后：按 foyofun-code-plan 输出实施计划 →
确认 → 直接实现（重构通常不需要骨架阶段；涉及大面积新建时可用 foyofun-code-stub）。
每改一个文件，核对调用方是否需要同步。

### 阶段 6：验证

- [ ] 所有原有调用方仍正常工作（签名变更全部同步）
- [ ] 是否需要 deprecated wrapper 兼容过渡
- [ ] 文件拆分/合并后引用路径正确
- [ ] foyofun-code-review 审查 diff：确认 diff 里**只有结构变化没有行为变化**

### 阶段 7：沉淀

重构中发现的新偏好模式（如"这个模块的切面划分值得参考"）→ 建议用户记入经验库。

## 重构反模式（必须避免）

**1. 为"干净"而过度拆分**——30 行函数拆成 10 个 3 行函数，维护者要跳 10 次。
拆分门槛：≥2 个调用方独立使用，或拆出的函数 ≥15 行。

**2. 为"解耦"而过度抽象**——单调用方却引入接口层+实现层。
抽象门槛：确有 ≥2 种实现或需要 mock 测试。经验库的抽象偏好优先于本条默认。

**3. 顺手"修一下"**——重构 diff 里混入行为修改，review 就无法区分结构变化和行为变化。
发现 bug：记入遗留清单，用轻量路径单独修，或重构完成后再修。

## 关键原则

1. **行为不变是底线**——验证阶段发现行为 diff 比发现 bug 更严重
2. **多方案而非单方案**——2-3 种覆盖光谱，用户选比 AI 定好
3. **经验库是罗盘**——用户对"好架构"的偏好记录在哪，就往哪走
4. **调用方影响必须明确**——改签名必改全部调用方
5. **反投机**——不为想象中的未来需求重构，只为确认的痛点或用户说清的铺路需求

# 项目代码调研（research）

## 设计背景

在大型项目中，开发前最常见的两个问题是：
1. **重复造轮子**——不知道已有类似功能，写了一遍又一遍
2. **理解错误**——凭印象理解现有模块，改的时候才发现和想的不一样

本 skill 是 f/g/h/i 的**强制前置步骤**——不拿调研结论就不能进入 Plan 阶段。

核心设计：**调研结论缓存 + Git 失效检查**，避免每次调研都从零开始搜索，节省大量 token。

---

## 路径配置

| 变量 | 说明 |
|------|------|
| `PROJECT_SRC_DIR` | 项目源码根目录（语言/框架无关，由环境提供或项目适配配置提供） |
| `RESEARCH_CACHE_DIR` | `${PROJECT_SRC_DIR}/.record/research-cache/` |

---

## 调研合格标准

调研结束时，以下**合格线**的全部 4 条必须打勾才算完成。良好线尽量达到，但不应为了良好线而通读整个文件。

### 合格线（必须达到）

- [ ] 找到了目标模块/功能的主要文件
- [ ] 确认了是否已有类似功能（避免重复造轮子）
- [ ] 列出了需要调用的已有接口（从 api-registry 交叉验证）
- [ ] 识别了数据来源（协议 / 配置表 / 本地计算）

### 良好线（尽量达到）

- [ ] 理解了主数据流走向（协议 → handler → logic → 存储，不超过 5 步）
- [ ] 提取了目标模块的编码风格（供 module-style 使用）
- [ ] 找到了至少一个可参考的相似实现

### 过度调研（应避免）

- 通读了整个文件而不是只看关键函数
- 追踪了所有分支调用链而不是只追主干
- 调研了松散相关的周边模块

## 执行流程

### 步骤 1：生成缓存键 & 查缓存

根据用户请求生成 `cache_key`（英文 slug，如"teamquick-guide-refactor"）：

```
缓存文件 = ${RESEARCH_CACHE_DIR}/{cache_key}.md
```

如果缓存文件存在，读取其 YAML 元数据头（前 ~15 行），然后执行失效检查：

**三层失效判断**：

| 检查层 | 方法 | 成本 |
|--------|------|------|
| 1. TTL | `researched_at + ttl_days > now` ? | 零额外 token |
| 2. Git diff | `git log --since="{researched_at}" --oneline -- {files_touched目录}` | 一次 Bash（几十 token） |
| 3. 用户强制 | 用户明确说"重新调研" | 零 token |

TTL 动态设定：

| 模块特征 | ttl_days | 理由 |
|---------|----------|------|
| 稳定框架层（ModuleBase、UIBase） | 30 | 半年不改一次 |
| 成熟业务模块（商城、背包） | 14 | 偶尔小修 |
| 活跃开发模块（当前迭代中的功能） | 7 | 改动频繁 |
| 未知模块 | 3 | 保守策略 |

- **缓存命中**（TTL 未过期 + Git 无新提交）→ 直接复用结论，跳到步骤 5 呈现
- **缓存失效**（任一条件触发）→ 继续步骤 2

### 步骤 2：检索路径（省 token 策略）

遵循三层检索，避免直接逐文件 Read：

```
1. 查 API 注册表 _flat_index.md（${PROJECT_SRC_DIR}/.record/api-registry/_flat_index.md）
   → 确认哪些接口已收录（~500-2000 tokens）
2. 查项目知识库 _flat_index.md（如项目配置了知识库）
   → 看目标模块是否已有文档
3. 知识库命中 → 读对应 _toc.md → 分段读正文
4. 知识库未命中 → 调用项目可用的代码探索工具去代码中搜索
```

代码搜索一律下沉到子 Agent 或 Grep 工具，主流程只做编排和合并。

### 步骤 3：执行调研

调用项目可用的代码搜索子 Agent（如 lua-code-explorer 或通用 code-explorer），按合格线清单逐项收集信息。

子 Agent prompt 模板：

```
## 任务
调研「{cache_key}」——用户需求是：{用户原始需求}

## 要求
1. 找到目标模块的主要文件
2. 确认是否已有类似功能
3. 列出需要调用的已有接口（重点：区分项目封装接口 vs 语言标准库接口）
4. 识别数据来源（协议 / 配置表 / 本地计算）
5. 如有余力：追踪主数据流、提取模块编码风格、找相似实现参考

## 参数
keywords: {关键词数组}
project_root: {PROJECT_SRC_DIR}
```

### 步骤 4：写缓存

调研结束后，按以下格式写入缓存文件：

```markdown
---
researched_at: ISO8601时间戳
ttl_days: 7
keywords: [关键词数组]
files_touched:
  - {文件路径}
apis_found:
  - {API完整签名}
related_modules: [关联模块名]
---

## 🔍 调研结论：{主题}

### 1. 已有相似功能
{具体分析，无相似则写"无"}

### 2. 涉及文件
| 文件 | 角色 | 需要改动？ |
|------|------|-----------|
| {路径} | {数据管理/UI展示/协议处理/配置} | 是/否 |

### 3. 需要调用的已有接口
| 接口 | 来源 | 已验证？ |
|------|------|---------|
| {完整签名} | api-registry / 本次调研发现 / 知识库 | ✅ / ⚠️ 需确认 |

### 4. 数据流
{简图，不超过 5 步}

### 5. 模块风格摘要
{命名风格、日志风格、注释风格、惯用模式}

### 6. 新 API 候选
{建议写入 api-registry 的接口列表，无则写"无"}
```

### 步骤 5：呈现结论 & 提示

原样呈现调研结论给用户。

如果步骤 4 中 `apis_found` 有新接口（不在 api-registry 已有条目中），追加提示：

```
💡 本次调研发现 {N} 个未收录的 API，是否写入 API 注册表？
```

用户确认后，调用 api-registry skill 的写入流程追加。

---

## 关键原则

1. **先查缓存，再调研**——节省 token 的第一步
2. **用代码搜索子 Agent 搜索代码**——主流程不直接逐文件 Read/Grep
3. **调研合格线必须全部打勾**——4 条缺一不可
4. **不过度调研**——只追主干，不通读所有文件
5. **TTL + Git 双重失效检查**——平衡时效性和效率

# 代码审查（foyofun-code-review）

## 设计背景

通用 code review 关注面太宽（性能、安全、风格、覆盖率……），输出冗长重点不突出。
对业务开发，真正要紧的是四件事：有没有不能合入的、逻辑对不对、日志合不合理、
API 选没选对。

**只审 diff**（本次改动），不审已有代码——旧代码的债是另一个任务，
混进来审会让报告失焦。

## 审查范围

```
git diff HEAD        # 已修改未 stage
git diff --cached    # 已 stage 未提交
```

两者合并覆盖全部未提交更改；无 git 的项目审查当前会话的改动记录；
用户指定文件则只审指定文件的 diff。

## 四个维度

### 1. 🔴 阻塞项（必须修复，不可合入）

| 检查项 | 说明 |
|--------|------|
| 使用不存在的 API | 拼写错误、捏造接口、参数个数不对 |
| 破坏现有调用链 | 改了签名但调用方未同步 |
| 全局副作用不可控 | 改全局/单例无防御检查 |
| nil/null 必然崩溃 | 返回值未判空直接取成员 |
| 死循环/无限递归 | 无退出条件 |
| 注册无注销 | 事件/定时器注册后无成对注销，且项目适配表注明**不兜底** |

检查方式：每个新增 API 调用经 foyofun-code-api 验证存在性。

### 2. 🟡 逻辑错误（很可能出 bug，逐条确认）

条件遗漏（`a > 0` 漏了 `a == 0`；`if data` 但 data 可能是空表）、
边界（越界/除零/空串/负值）、时序假设（假设 A 先于 B 但无保证）、
状态残留（切换/退出未清理 timer、listener、cache）、
类型混用（`"0"` vs `0`）、nil 传递链（A 返回 nil → B 不查 → C 崩）。

### 3. 📝 日志

判断标准：**这个函数出 bug 时，现有日志能不能定位到哪一步出的问题？**

- 关键路径：函数入口、关键分支、外部依赖调用（协议/配置/IO）返回值、错误分支
- 过度打印：循环内全量打印（N 轮循环就是 N 条日志，几轮就把真信息淹了）——
  只在异常分支打，或循环前后汇总打；高频回调（每帧/滚动）同理
- 具体指出"第 X 行缺日志""第 Y 行循环内全量打印"，不浮于表面

### 4. 🔧 API 选择

对比 `<project>/.agents/api/` 积累：diff 中是否存在该用项目封装却用了通用 API 的调用
（如 `os.time()` 而非 `TimeUtil.GetServerTimeInSec()`）。命中红线逐条列出改法。

## 输出格式

```markdown
## 🔍 Review：{审查范围}

### 🔴 阻塞项（{N} 个 / ✅ 无）
| # | 文件:行号 | 问题 | 修复建议 |

### 🟡 逻辑问题（{N} 个 / ✅ 未发现）
| # | 文件:行号 | 问题场景 | 修复建议 |

### 📝 日志
| 检查项 | 状态 |

### 🔧 API 选择（✅ 已正确使用项目封装 / 问题表）

### 📊 总结
整体评估：✅ 可合入 / ⚠️ 修复后合入 / 🔴 有阻塞项不可合入
```

## 轻量模式（小改动使用）

≤30 行的小改动：逐行指出问题，不分维度，只写有问题的部分 + 一句结论。

## 关键原则

1. **只审 diff**——旧代码的债另开任务
2. **阻塞项措辞明确**——不用"建议""可能""考虑"，是就是
3. **风格问题不评**——除非违反经验库明确记录的偏好（foyofun-code-experience）
4. **审查 ≠ 批评**——目标是合入前拦截风险，不是展示 findings 数量

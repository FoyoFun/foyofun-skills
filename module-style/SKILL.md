# 模块风格分析（module-style）

## 设计背景

在 3 万+ 文件的大型项目中，不同模块由不同的开发者和团队维护，自然形成了不同的编码习惯。
例如：模块 A 习惯用大驼峰命名私有方法，模块 B 习惯用下划线；模块 A 在循环中全量打日志，
模块 B 只在异常分支打。

AI 受训练数据影响，会按"通用的最佳实践"写代码——但在一个特定模块里，
"最佳实践"就是**和已有代码看起来像一个人写的**。本 skill 不做抽象的风格规范，
只做一件事：读 2-3 个已有函数，提取风格特征，让后续代码入乡随俗。

---

## 使用场景

- 在已有 logic 模块中新增功能 → logic-dev 调用本 skill
- 在已有 UI 模块中新增控件逻辑 → ui-dev 调用本 skill
- 重构一个模块 → code-refactor 调用本 skill
- 小修一个函数 → quick-fix 调用本 skill（轻量版）
- 用户明确要求"分析这个模块的风格"

---

## 执行流程

### 步骤 1：确定目标模块

从用户请求或 research 调研结论中，确定目标模块的文件路径。

如果没有明确的目标文件，跳过本 skill——开新模块不需要风格分析。

### 步骤 2：选取样本函数

从目标文件中选 **2-3 个函数**作为样本。选取规则：

- 优先选 `function ClassName:XXX()` 形式的公开方法（最能代表模块对外风格）
- 包含一个 ~10-30 行的中等函数（小函数信息量不够，大函数读取成本高）
- 如果文件 ≤ 50 行，只读 1 个函数即可

使用 `search_content` 按 `^function\s+\w+:` 搜索函数定义行，
然后 Read 函数体（从定义行读到下一个函数定义或文件尾）。

### 步骤 3：提取风格特征

从样本函数中提取以下维度：

#### 3.1 命名风格

| 检查项 | 示例 |
|--------|------|
| 公开方法 | `OnClick()` / `on_click()` / `HandleClick()` |
| 私有方法 | `_DoSomething()` / `doSomething()` / `_do_something()` |
| 局部变量 | `local myVar` / `local my_var` / `local MyVar` |
| 常量 | `MAX_COUNT` / `MaxCount` / `kMaxCount` |
| 参数名 | `playerUid` / `player_uid` / `uid` |

#### 3.2 注释风格

| 检查项 | 回答 |
|--------|------|
| 函数注释类型 | LDoc (`---@param`) / 行注释 (`-- xxx`) / 无注释 |
| 注释语言 | 中文 / 英文 / 双语 / 无明确规律 |
| 注释位置 | 函数上方 / 行内 / 行上方 |
| 行内注释密度 | 几乎每行 / 只在关键行 / 很少 |

#### 3.3 日志风格

| 检查项 | 回答 |
|--------|------|
| 日志函数 | `log()` / `log_format()` / `printf()` / `log_warning()` / `log_error()` |
| 前缀格式 | `ClassName:FuncName` / `ClassName.FuncName` / `[ClassName]` / 无前缀 |
| 日志语言 | 英文 / 中文 |
| for 循环内日志 | 全量打印 / 只在异常分支打 / 循环内不打 |
| 关键路径埋点 | 入口+出口都打 / 只在入口打 / 只打异常 |

#### 3.4 惯用模式

| 检查项 | 示例 |
|--------|------|
| 定时器 | `self:AddTimerLoop()` / `time_ticker` / `Timer.Add()` |
| 空值检查 | `if not x then return end` / `if x == nil then` / `assert(x)` |
| 错误处理 | 静默 return / 打日志后 return / 弹窗提示 |
| 数据遍历 | `for i, v in ipairs` / `for k, v in pairs` / `table.foreach` |
| UI 数据刷新 | 全量刷新 / 增量刷新 / `SetData` 后局部 `SetItemData` |

### 步骤 4：输出风格摘要

```markdown
## 🎨 模块风格摘要：{模块名/文件名}

### 基本信息
- 分析样本：{N} 个函数（{函数名列表}）
- 文件路径：{路径}

### 命名
| 类型 | 风格 | 示例 |
|------|------|------|
| 公开方法 | {大驼峰/下划线/...} | {示例} |
| 私有方法 | {前缀 _ 大驼峰/...} | {示例} |
| 变量 | {小驼峰/下划线/...} | {示例} |

### 注释
- 格式：{LDoc / 行注释}
- 语言：{中文 / 英文 / 双语}

### 日志
- 函数：{log / log_format / printf}
- 前缀：{ClassName:FuncName}
- 循环内：{只在异常打 / 全量打 / 不打}

### 惯用模式
- 定时器：{AddTimerLoop / Timer.Add}
- 空值检查：{if not x then return end}
- 数据刷新：{全量 / 增量}
```

### 步骤 5：应用规则

在后续实现中：

1. **命名**：严格匹配目标模块风格（即使和 api-registry / experience-repo 的建议不同，以模块现有风格为准）
2. **注释**：格式和密度和已有代码一致
3. **日志**：用相同的函数、相同的前缀格式
4. **惯用模式**：优先用模块已有模式（如模块用 `self:AddTimerLoop`，就绝不用 `time_ticker`）

---

## 轻量模式（quick-fix 使用）

quick-fix 涉及文件少、改动小，不需要完整的风格分析。改为：

1. Read 目标文件中当前函数所在区域的 ~50 行上下文
2. 观察命名、注释、日志风格
3. 新代码风格和上下文对齐（不需要输出完整的风格摘要）

---

## 关键原则

1. **入乡随俗**——目标模块的风格 > 全局规范 > AI 的"最佳实践"
2. **样本够用就行**——2-3 个函数，不需要通读整个文件
3. **风格摘要不是规范文档**——它只描述"这个模块怎么写"，不判断好坏
4. **当模块风格和用户经验冲突时**——优先模块风格（因为维护该模块的人习惯了）
5. **新模块无样本时跳过**——不需要分析

## 与其他 Skill 的关系

| Skill | 关系 |
|-------|------|
| research | research 调研结论中的"模块风格摘要"是粗粒度的，module-style 是精读版 |
| experience-repo | 经验库记录的是"通用偏好"，module-style 记录的是"这个模块的既成事实" |
| logic-dev / ui-dev / code-refactor / quick-fix | 实现前必调，产出风格摘要指导后续代码 |

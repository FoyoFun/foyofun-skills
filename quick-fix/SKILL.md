# 快速修复（quick-fix）

## 设计背景

不是每个改动都需要走完整的"调研 → Plan → 实现 → Review"流程。
有时只是清一个 TODO、改一个判断条件、调整一个参数、加两行日志——
这些轻量改动的核心诉求是**快**，但也需要**准**。

quick-fix 是 logic-dev / ui-dev / code-refactor 的降级版：
跳过 Plan 阶段，但保留最小化的调研和验证。

---

## 适用场景（满足任一即可）

| 场景 | 示例 |
|------|------|
| TODO 清理 | "帮我把这个 TODO 实现了" |
| 小功能补充 | "给这个函数加上 XX 逻辑" |
| 局部 Bug 修复 | "这里判断条件漏了，补一下" |
| 日志补充 | "关键路径上加一行日志" |
| 参数调整 | "把 30 改成可配置的" |
| 空值检查补充 | "这里可能 nil，加上安全检查" |
| 循环优化 | "这个循环里把那个判断提取出来" |
| 局部重构 | "这个 50 行函数里的后 20 行抽成独立函数" |

---

## 规模阈值（硬标准）

```
✅ quick-fix 适用：
  - 改动 ≤ 30 行
  - 涉及文件 ≤ 2 个
  - 不新增文件

⚠️ 超过阈值 → 自动升级：
  - 30-100 行或 3-5 个文件 → logic-dev / ui-dev
  - 涉及重构 → code-refactor
  - 新增文件 → logic-dev / ui-dev
```

## 执行流程（极简）

### 步骤 1：轻量调研（~30 秒）

不需要调用完整的 research skill。只看：

1. Read 目标函数及其上下 20 行
2. 确认改动的边界（影响范围不会超出这个函数/文件）
3. 如果有 API 调用，在 api-registry `_flat_index.md` 中快速 check

### 步骤 2：轻量风格对齐

不需要调用完整的 module-style。只看目标函数周围的代码风格：
- 变量命名方式
- 注释习惯
- 日志前缀格式

新代码和上下文保持一致即可。

### 步骤 3：轻量经验检查（可选）

如果涉及命名/抽象/切面决策（如"要不要把这段提取为函数"），
快速扫一眼经验库对应分类。不涉及则跳过。

### 步骤 4：实现

直接修改。一个改动完成后，如果有第二个独立的小改动，询问用户是否继续。

### 步骤 5：轻量自检

用 change-review 的轻量模式快速过一遍：

```
- 用的 API 项目里都有吗？
- 关键路径有日志吗？（新增逻辑不加日志 = 出 bug 没法查）
- 循环里有全量打印吗？
- 有没有随手"顺便"改了无关的东西？
```

## 典型示例

### 示例 1：清理 TODO

```
用户: "帮我把第 42 行的 TODO 实现了"
```

```
1. Read 目标代码 → 理解 TODO 要做什么
2. Read api-registry _flat_index → 确认需要的 API
3. 写 3-5 行实现
4. 删 TODO 注释
5. "✅ 已实现 {描述}，改动 {N} 行"
```

### 示例 2：补充空值检查

```
用户: "这里 data 可能为 nil，加个安全检查"
```

```
1. Read 目标行 → 理解上下文
2. 加 nil 检查（和模块现有风格一致）
3. 如果模块风格是 `if not data then return end`，就不要用 `if data == nil then`
4. "✅ 已添加 nil 检查，风格与模块一致"
```

### 示例 3：循环优化

```
用户: "这个 for 循环里的全量日志太多了，改成只在异常条件下打印"
```

```
1. Read 循环体 → 识别异常条件
2. 把全量 log 移入 if 分支
3. "✅ 已调整日志位置——从每轮打印改为只在 {异常条件} 时打印"
```

```markdown
## 🔍 快速审查

### 改动
{文件}:{行号} — {一句话说明改了啥}

### 检查
- API 存在性：✅ / ⚠️ {具体问题}
- 日志：✅ / ⚠️ {缺少/过度}
- 其他：✅ / 💡 {建议}

### 结论
✅ 无问题 / ⚠️ {N} 个小建议
```

---

## 关键原则

1. **快但不糙**——调研可以轻量但不能跳过（至少确认 API 存在）
2. **改动范围严格约束**——不要"顺便"改无关代码
3. **超过阈值就升级**——不要硬撑，30 行的限制是保护代码质量的底线
4. **风格对齐上下文**——周围代码怎么写你就怎么写

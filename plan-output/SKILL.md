# 方案输出模板（plan-output）

## 设计背景

AI 输出的方案常常格式不统一：有的太简略（"改 X 文件加 Y 函数"），
有的太啰嗦（贴大段代码），用户需要反复追问才能理解全貌。

本 skill 提供一个标准模板，所有 Layer 3 skill（logic-dev / ui-dev / code-refactor）
在"方案输出"阶段都按此格式呈现。模板的核心设计理念：

1. **先总后分**——从概述到细节，用户可以按需深入
2. **改动清单表格化**——一目了然，便于评估影响面
3. **关键决策显式化**——把 AI 不确定的点列出来，而不是藏在心里
4. **数据流可视**——用文字简图代替长篇描述

---

## 方案输出格式

```markdown
## 📋 方案：{一句话标题}

### 1. 需求概述
{1-2 句话，说清楚要做什么。不写背景故事，只写"输入→输出"}

### 2. 涉及文件
| # | 文件 | 改动类型 | 说明 |
|---|------|---------|------|
| 1 | {路径} | 新增/修改/仅参考 | {改了什么、为什么} |

**改动量估算**：新增 ~{N} 行 / 修改 ~{M} 行 / 新增 {K} 个文件

### 3. 数据流
```
{协议/配置/事件} → {handler/logic} → {存储/状态变更} → {通知UI/其他模块}
```
{数据流每一步的简要说明，不超过 5 步}

### 4. 关键接口
| 接口（新增/修改） | 签名 | 职责 |
|------------------|------|------|
| 新增 | `function Xxx:Yyy(uid, data) → result` | {一句话职责} |
| 修改 | `function Xxx:Zzz()` 补充 {描述} | {改了什么} |

> **原则**：如非必要，勿增接口。优先在现有接口中补充逻辑。

### 5. 关键决策点
{列出需要用户确认的问题，每个一行}
- 🔴 {阻塞性问题：不改方案就无法进行}
- 🟡 {选择性问题：有多个合理方案，推荐 {X}，理由：...}

### 6. 边界条件 & 风险
| 场景 | 处理方式 | 风险 |
|------|---------|------|
| {nil 输入} | {怎么处理} | {低/中/高} |
| {时序冲突} | {怎么处理} | {低/中/高} |
| {已有调用方受影响} | {兼容方式} | {低/中/高} |

### 7. 参考实现（如有）
- {文件路径} 中的 `{函数名}` — {可参考的具体方面}
```

## 使用规则

### 何时用完整模板 vs 精简版

| 改动规模 | 使用的模板 |
|---------|-----------|
| 新增模块 / ≥3 个文件 / ≥100 行 | **完整模板**（7 个 section 全写） |
| 修改 1-2 个文件 / 30-100 行 | **精简版**（1/2/4/5 必写，其余按需） |
| ≤30 行 / 1 个文件 | **不用模板**（quick-fix 直接一句话说明） |

### 精简版最低要求

```markdown
## 📋 方案：{标题}

### 改动
{文件路径} — {改了什么，3 行以内}

### 关键决策
{有不确定的才写，没有就省略}
```

---

## 输出后的交互

方案输出后，不要立即开始编码。等待用户反馈：

- 用户说"可以"、"开始吧"、"没问题" → 进入实现阶段
- 用户提出修改 → 更新方案后再次确认
- 用户说"这里再详细一点" → 补充对应 section 的细节
- 用户沉默 > 2 轮未回应 → 追问一次"方案是否可行？"

---

## 关键原则

1. **表格优先于段落**——表格扫一眼就懂，段落需要逐行读
2. **关键决策摆上台面**——不要替用户做决定，把选项和推荐理由列出来
3. **数据流是方案的骨架**——从数据视角看问题，比从文件视角更清晰
4. **改动量估算是诚意**——让用户对工作量有预期，避免"我以为就改两行结果改了一下午"

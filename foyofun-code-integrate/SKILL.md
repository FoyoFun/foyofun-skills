# ui 与 logic 集成（foyofun-code-integrate）

## 设计背景

分头闭环开发的必然产物是：两侧各留着 `[SEAM]` 契约桩和 `[MOCK]` 假数据点。
集成不是"继续开发"，而是**装配**：把桩填上、把假换真、把事件绑上。
装配的本质决定了两条纪律：

1. **只增不改**——两侧代码都已通过各自的闭环测试，改动它们等于引入未验证的风险；
   集成中发现的任何问题，记录下来，该修的走 foyofun-code-refactor 或单独修
2. **契约不一致时暴露给用户裁决**——禁止默默改一侧去迁就另一侧

## 执行流程

### 阶段 1：调研（foyofun-code-research，强制）

重点搜索两类标记形成**对接清单**：
- `[SEAM]`——契约桩：谁拥有、什么形状、是否已填
- `[MOCK]`——假数据点：假的是什么、替换成什么真源

同时确认：logic 快照/intent 接口是否已实现、UI 事件订阅点在哪、
协议/美术资源是否真的就绪了。

### 阶段 2：契约核对

对照 Plan 的契约段（快照形状/意图清单/事件清单）逐项检查两侧：

- 快照字段名/类型/可空性两侧一致？
- UI 发出的每个意图，logic 侧有对应接口？
- 事件名、载荷结构、谁发谁收明确？

**不一致项列成表交给用户**：{字段/意图/事件} | ui 侧认为 | logic 侧认为 | 建议。
用户裁决前不动手。如果当初没写契约段，本阶段先补一份契约再核对。

### 阶段 3：装配（只增不改）

按对接清单逐项执行：

1. **填桩**：logic 侧填充自己拥有的 `[SEAM]`（如快照 getter 的真实现）——
   填充后删除 `[SEAM]` 标记
2. **换源**：UI 侧 `[MOCK]` 假数据源换成真调用（`logic:GetXxxSnapshot()`）——
   替换后删除 `[MOCK]` 标记
3. **绑事件**：UI 的注册区分发事件订阅 + 回调里重拉快照并刷新
4. **接意图**：UI 意图分发点从打日志改为调 logic 接口

### 阶段 4：时序处理

按 Plan 时序表核对跨层时序，缺的补上：
- 打开期请求：OnShow → Ensure（去重由 logic 兜）
- 变更通知：数据落地 → 事件 → UI 重拉快照 → 刷新
- 多源聚合：真实数据源接入后验证聚合收敛（轮询对账仍保留）
- 呈现级时序（按钮冷却、动画）确认仍在 UI 侧未被搬动

### 阶段 5：冒烟验证

真链路走一遍：打开界面 → 触发请求 → 数据到达 → 渲染正确；
每个意图走一遍：操作 → 接口调用 → 状态变化 → 反馈呈现。
清理确认：`[SEAM]`/`[MOCK]` 全部消除（保留的要有明确理由）。

### 阶段 6：自检（foyofun-code-review）+ 收尾

- 改动清单（应该全部是"新增/填充"）提交 review
- 遗留问题清单（契约不一致的裁决结果、发现的老 bug）转给用户
- 集成中确认过的新 API → 收录进 api 积累

## 关键原则

1. **只增不改**——装配不是开发；两侧已验证的代码是资产不是障碍
2. **不一致上桌**——契约冲突是用户决策，不是 AI 的自由裁量
3. **标记清零**——`[SEAM]`/`[MOCK]` 是债务，集成完成即清偿
4. **发现缺陷记录而非顺手修**——集成 diff 里混进行为修改，review 就无法验证装配正确性

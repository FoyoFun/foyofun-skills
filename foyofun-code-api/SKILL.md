# 项目 API 查询与积累（foyofun-code-api）

## 设计背景

AI 天然倾向用训练数据里的通用 API（`os.time()`、`string.split`、原生字符串拼接），
但项目通常有更合适的封装（`TimeUtil.GetServerTimeInSec()`、`StringUtil.Split()`）。
项目封装处理了时区、nil 安全、热更兼容等问题，直接用通用 API 会埋隐藏 bug。

## 核心红线

> **存在同功能的项目 API 时，使用通用 API 是绝对禁止的。**

## 查询流程

### 步骤 1：查积累（零成本路径）

Read `<project>/.agents/api/_index.md`，命中分类则读分类文件确认签名与用法。

### 步骤 2：启发式判断"该不该有项目 API"

以下类别**几乎必然存在项目封装**，查不到积累时必须搜索项目代码确认：

| 类别 | 典型封装形态 |
|------|-------------|
| 时间 | TimeUtil / DateUtil（服务器时间、格式化、同天判断） |
| 字符串 | StringUtil（分割、拼接、格式化） |
| 表/集合 | TableUtil（排序、查找、深拷贝、长度） |
| 日志 | 项目统一 log 函数（别用 print / Console.Write） |
| UI 组件 | 通用控件操作（SetData/InitView/刷新） |
| 事件 | 项目事件系统（注册/发送） |
| 定时器 | 项目定时器管理（统一清理） |
| 网络 | 协议收发封装 |
| 配置表 | 配置读取接口 |
| 文件/资源 | 路径与加载封装 |

其他类别（纯数学计算等）查不到积累时可先按通用 API 处理，但要在实现说明中标注。

### 步骤 3：搜索项目代码

Grep 功能关键词（如 `Split`、`GetServerTime`），找到封装 → 确认签名存在且可调用。
项目适配表（`<project>/.agents/adaptation.md`）里"已知项目封装分类"一节
会列出本项目实际有哪些封装类，优先按它定向。

### 步骤 4：三选一使用

1. 有项目封装 → **必须用项目封装**
2. 搜不到封装 → 用通用 API，实现说明中标注"未找到项目封装，用了通用 API"
3. 连通用 API 都不确定存在（弱类型语言/拼写没把握）→ 停下，标注 `-- TODO: 需确认 {签名} 是否存在`

### 步骤 5：回写积累

本次搜索确认过的接口，追加到 `<project>/.agents/api/` 对应分类文件（没有就新建），
格式：

```markdown
### `TimeUtil.GetServerTimeInSec() → number`
获取服务器时间（秒）。**替代 `os.time()`**——后者是本地时间，与服务器可能不一致。
常用于：倒计时、活动时间判断。
```

要点：签名直接可复制；**"替代了哪个通用 API"必须写**——这是给未来的 AI 看的
反面清单；有常见误用加 ⚠️ 警告。每次回写前先查重。

## 积累目录结构

```
<project>/.agents/api/
├── _index.md      # 分类路由表（分类 | 文件 | 一句话说明）
├── time.md
├── string.md
├── ui-widget.md
└── ...            # 按需新增
```

## 用户主动收录

用户说"记录这个接口""收录到 API 库"时：判定分类 → 查重 → 按上述格式追加 →
更新 `_index.md` → 告知用户"✅ 已收录 {签名} 到 {文件}"。

## 关键原则

1. **先查积累再搜代码**——积累命中是零成本路径
2. **启发式类别宁可多搜一次**——漏查的代价（隐藏 bug）远大于多一次 Grep
3. **每次搜索的结论都沉淀**——这是跨对话一致性的来源
4. **人可读可改**——用户可以直接增删条目，下次查询即生效

## 与其他 Skill 的关系

| Skill | 关系 |

| foyofun-code-research | 调研发现的接口经本 skill 验证后回写积累 |

| foyofun-code-stub | 已验证的 API 签名直接写入骨架，实现者不再二次查询 |
| foyofun-code-review | 审查时用积累做"通用 API 误用"对照 |

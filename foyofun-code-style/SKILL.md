# 模块风格分析（foyofun-code-style）

## 设计背景

不同模块由不同人维护，形成了不同的既成习惯：大驼峰 vs 下划线、协议函数 snake_case
而其余 PascalCase、循环内打不打日志……AI 受训练数据影响倾向写"通用最佳实践"，
但在一个特定模块里，**最佳实践就是和已有代码看起来像一个人写的**。

本 skill 不做抽象风格规范，只做一件事：读少量样本，提取风格特征，让新代码入乡随俗。

## 优先级规则（整套 skill 体系的通用规则）

> 模块既成事实（本 skill） > 项目经验 > 个人经验（foyofun-code-experience） > skill 默认原则

在已有模块上写代码，风格冲突时永远听模块的。

## 执行流程

### 步骤 1：确定目标文件

从用户请求或调研结论中确定目标文件。**新建文件跳过本 skill**
（新文件按经验库和标准结构模板走）。

### 步骤 2：选取样本

从目标文件选 **2-3 个函数**：
- 优先选有代表性的公开方法（最能体现模块对外风格）
- 包含一个 ~10-30 行的中等函数（小函数信息量不够，大函数读取成本高）
- 文件 ≤ 50 行时只读 1 个即可

### 步骤 3：提取特征

| 维度 | 检查项 |
|------|--------|
| 命名 | 公开/私有方法、局部变量、常量、参数名各用什么风格 |
| 注释 | 文档注释格式（LDoc/XML doc/无）、语言（中/英）、密度 |
| 日志 | 用什么函数、前缀格式（`Class:Func`/`[Class]`）、循环内打不打、关键路径埋点习惯 |
| 惯用模式 | 定时器写法、空值检查写法（`if not x then return end` vs `if x == nil`）、错误处理、遍历方式 |

注意：**命名的不对称是常态**（如协议函数用 snake_case、其余用 PascalCase）。
发现这类惯例要记录并遵守，不要"修正"它。

### 步骤 4：输出风格摘要

```markdown
## 🎨 风格摘要：{文件名}
- 样本：{函数名列表}
- 命名：{公开/私有/变量各什么风格，特例惯例}
- 注释：{格式 / 语言 / 密度}
- 日志：{函数 / 前缀 / 循环内策略}
- 惯用：{空值检查 / 错误处理 / 其他显著模式}
```

摘要供两个消费者使用：当前会话的实现阶段直接参考；
foyofun-code-stub 生成骨架时内嵌进骨架注释（供后续实现者遵守）。

## 轻量模式（小改动使用）

改动 ≤ 30 行时不需要完整分析：Read 目标函数上下 ~50 行，
观察命名/注释/日志风格，新代码直接对齐，不输出正式摘要。

## 关键原则

1. **入乡随俗**——模块风格压过一切规范和 AI 的"最佳实践"
2. **样本够用就行**——2-3 个函数，不通读文件
3. **只描述不评判**——风格摘要说的是"这个模块怎么写"，不判断好坏
4. **新模块无样本则跳过**——不要硬套

## 与其他 Skill 的关系

| Skill | 关系 |
|-------|------|
| foyofun-code-research | 调研结论若含粗粒度风格信息，本 skill 是它的精读版 |
| foyofun-code-experience | 经验库记的是用户通用偏好，本 skill 记的是该模块的既成事实，冲突时本 skill 赢 |
| foyofun-code-logic / ui / refactor | 实现与骨架生成前的必调步骤 |
| foyofun-code-stub | 风格摘要会被内嵌进骨架，让后续实现者（人或弱模型）自动遵守 |

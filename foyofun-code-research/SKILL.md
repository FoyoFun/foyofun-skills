# 项目代码调研（foyofun-code-research）

## 设计背景

开发前最常见的两个问题：**重复造轮子**（不知道已有类似功能）和**理解错误**
（凭印象理解现有模块，改的时候才发现和想的不一样）。本 skill 用一次有边界的调研解决它们。

反投机原则：调研只回答"当前任务的对接点在哪里、已有什么可用"，
不做"以后可能有用"的储备性调研。

## 步骤 0：项目引导（仅首次）

定位项目根目录（`.git` 所在层或源码顶层），检查 `<project>/.agents/` 是否存在：

**不存在** → 创建并初始化三样（模板见 `~/.agents/skills/README.md`）：
- `adaptation.md` —— 项目适配表骨架，提示用户："适配表已生成，建议现在填写项目框架信息；也可以先跳过，后续任务按需补齐。"
- `experiences/_index.md` —— 项目经验索引骨架
- `api/_index.md` —— API 积累索引骨架

**已存在** → 直接读 `adaptation.md`。适配表描述本项目框架的真实形态
（生命周期方法名、事件系统、定时器、注销是否框架兜底等），后续所有判断以它为准。

## 步骤 1：读项目知识（已沉淀的部分）

按下述顺序读索引，语义匹配命中才读分类文件，全部未命中就跳过：

1. `<project>/.agents/adaptation.md`
2. `<project>/.agents/experiences/_index.md`
3. `<project>/.agents/api/_index.md`

## 步骤 2：搜索项目代码

用 Grep 关键词 + Read 关键函数的方式收集，**只追主干，不通读文件**：

1. **已有相似功能**——找到了就评估：能直接用？能扩展？还是必须新写？
2. **数据来源**——每项数据属于哪类：协议下发 / 配置表 / 本地计算 / 其他模块持有
3. **可调用的接口**——区分项目封装与语言标准库（交给 foyofun-code-api 判定）
4. **对接桩**（仅集成/对接任务）——搜索 `\[SEAM\]` 与 `\[MOCK\]` 标记，
   形成"待对接清单"（这些标记的定义见 foyofun-code-stub）

## 步骤 3：输出调研结论

```markdown
## 🔍 调研结论：{主题}

### 1. 已有相似功能
{具体分析；无则写"无"，并说明搜索过的关键词}

### 2. 涉及文件
| 文件 | 角色 | 需要改动？ |
|------|------|-----------|

### 3. 数据来源
| 数据 | 来源类型 | 具体出处 |

### 4. 可用接口
| 接口 | 来源 | 状态 |
|------|------|------|
| {签名} | api 积累已收录 / 本次发现 / ⚠️ 需确认 | ✅/⚠️ |

### 5. 参考实现（如有）
- {文件} 的 {函数} — {可参考什么}
```

## 合格线（全部打勾才算完成）

- [ ] 目标模块/功能的主要文件已定位
- [ ] 相似功能有无已确认
- [ ] 每项数据来源已识别
- [ ] 需调用的接口已列出并标注验证状态

**过度调研红线**：不通读整个文件、不追所有分支调用链、不调研松散相关的周边模块。

## 出口

- 结论交给调用方（plan 阶段 / 直接实现）。
- 本次发现的有价值新接口 → 建议用户收录进 api 积累（`<project>/.agents/api/`）。
- 集成任务的对接清单交给 foyofun-code-integrate。

## 与其他 Skill 的关系

| Skill | 关系 |
|-------|------|
| foyofun-code-logic / ui / integrate / refactor | 前置步骤，本 skill 是它们调研阶段的执行者 |
| foyofun-code-api | 调研中发现的接口经它验证后收录积累 |
| foyofun-code-experience | 调研前先查经验索引，避免重复踩已记录的坑 |
| foyofun-code-stub | `[SEAM]`/`[MOCK]` 标记的定义方，集成调研靠它索引对接点 |

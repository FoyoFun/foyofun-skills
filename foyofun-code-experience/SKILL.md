# 编码经验库（foyofun-code-experience）

## 设计背景

AI 在代码架构上的判断（耦合/内聚/可读性/可维护性/抽象时机的平衡）和人的经验差距很大。
抽象规则无法传达这种微妙的平衡感，但**具体的正反例对比**可以有效缩小差距——
这是经验库的核心机制：每条经验 = 场景 + ✅ 推荐 + ❌ 不推荐 + 原因。

## 路径与优先级

| 层 | 路径 | 用途 |
|----|------|------|
| 个人经验 | `~/.agents/experiences/` | 跨项目的通用编码审美 |
| 项目经验 | `<project>/.agents/experiences/` | 本项目特有约定，不污染其他项目 |

读取时两层都查，项目经验优先于个人经验；两者都低于目标模块的既成事实
（见 foyofun-code-style 的优先级规则）。

## 经验条目格式

```markdown
## 经验：{一句话标题}

**场景**：{什么时候适用这条经验}

### ✅ 推荐
{代码块或具体做法}

### ❌ 不推荐
{代码块或具体做法}

**原因**：{为什么这样更好——这是整条经验的灵魂，必须写清}

**层级**：个人 / 项目（{项目名}）
**时间**：YYYY-MM-DD
```

格式必须**人可读、人可改**——用户看到记录不满意时会直接编辑文件本身。

## 读取流程（实现前）

1. Read 两层 `_index.md`（很短，~200 tokens）
2. 按当前任务语义匹配相关分类（写 UI → naming/abstraction；重构 → cross-cutting/interface-design）
3. Read 命中分类的文件，检查适用条目
4. 实现中遵守：有匹配 → 按推荐做法写；无匹配 → 自由发挥
5. 明显不涉及的分类直接跳过，不要全读

## 保存流程（用户描述偏好时）

触发词："记住""记一下""以后遇到这种""我的习惯是""不要这样写""这样写更好""这个经验记录一下"。

1. **从上下文确认四要素**：场景 / 推荐 / 不推荐 / 原因。用户没说清"原因"时，
   按你的理解补写，并标注"(AI 推断)"让用户可改。
2. **选层级**：跨项目通用 → 个人；本项目特有 → 项目。不确定 → 默认个人，同时告知用户。
3. **判分类**：naming / traversal / abstraction / cross-cutting / logging / interface-design / …
   现有分类都不匹配就新建文件。
4. **查重**：Read 目标分类文件，完全相同的不记；相似但不相同的追加为新条目。
5. **追加到文件尾部 + 更新 `_index.md`**（新分类才需要）。
6. **告知用户**：

```
✅ 已记录到 {个人/项目}经验库 → {文件}
📝 {一句话概括}
📍 {文件路径}
如有不妥可直接编辑该文件。
```

## 查看流程

用户说"查看经验库""我有哪些经验"时：列出两层所有分类及条目数（表格），
用户点名分类再展开正文。

## 关键原则

1. **正反例比抽象描述有效十倍**——用代码说话
2. **人机共读共改**——用户随时能直接编辑文件
3. **经验 ≠ 铁律**——有匹配时参考，场景明显不同时可灵活处理并在方案中说明
4. **增量积累**——每次用户纠正 AI 都是一次记录机会，主动建议记录

## 与其他 Skill 的关系

| Skill | 关系 |
|-------|------|
| foyofun-code-logic / ui / refactor | 实现前加载，是它们的"审美罗盘"；refactor 尤其依赖 |
| foyofun-code-stub | 适用条目会内嵌进骨架注释，让实现者自动遵守 |
| foyofun-code-style | 冲突裁决：模块既成事实 > 经验库 |
| foyofun-code-review | 审查时用经验库检查是否违反偏好的写法 |

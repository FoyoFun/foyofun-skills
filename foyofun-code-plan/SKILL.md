# 方案输出模板（foyofun-code-plan）

## 设计背景

AI 输出的方案常有两个失败模式：太简略（"改 X 文件加 Y 函数"），或自作主张
（把没确认的假设当事实写进去）。本模板用固定结构对抗两者：信息来自调研结论而非想象，
所有不确定点显式列出让用户裁决——**不确定的问题列出来等回答，比猜一个写进去好十倍**。

## 完整模板

```markdown
## 📋 方案：{一句话标题}

### 1. 数据来源（已存在的，来自调研）
| 数据 | 来源 | 可靠性 |
|------|------|--------|
| {数据名} | 协议 XX / 配置表 XX / {模块}已有接口 | ✅ 已验证 / ⚠️ 待确认 |

> 目的：供用户检查每项数据来源是否真实可靠。⚠️ 项必须在"不确定点"中列出。

### 2. 时序逻辑
| 流程/数据项 | 触发 | 调度 | 呈现 |
|------------|------|------|------|
| {如成员列表} | 进界面/切页签（ui） | TTL+去重（logic） | 占位→刷新（ui） |

> 触发=谁表达需求；调度=何时真发请求/重算（去重、TTL、节流收敛在哪层）；
> 呈现=数据到达后的过渡（loading、动画）。定时器类需求按生命周期归属：
> 需求只存在于界面打开期间 → ui；与界面无关 → logic。

### 3. 新增逻辑与接口
| 类型 | 名称/位置 | 功能 | 原因 |
|------|----------|------|------|
| 新增接口 | `Xxx:Yyy(uid)` | {一句话} | {≥2 调用方 / 关注点不同} |
| 修改接口 | `Xxx:Zzz()` 补充{...} | {一句话} | 现有接口内可容纳 |

> 如非必要勿增接口：≤10 行逻辑直接改现有接口；
> 新建接口需满足 a)≥2 调用方 b)现有接口~80行且新逻辑≥30行 c)关注点完全不同 之一。

### 4. 对接契约（跨 ui/logic 的任务必填）
- **快照形状**：`{ field1: type, field2: type, ... }`（UI 渲染所需的最小数据集）
- **意图清单**：用户操作 → 对应 Ensure 型接口/事件
- **事件清单**：事件名 → 载荷 → 谁发谁收
- 对接点在骨架阶段打 `[SEAM]` 标记，集成期由 foyofun-code-integrate 消费

### 5. 不确定点（🔴 必须由用户回答）
- 🔴 {问题}：{你已经掌握的线索，帮助用户回答}
- 🟡 {选择题：有多个合理方案，推荐 X，理由}

### 6. 参考实现（如有）
- {文件} 的 {函数} — {可参考什么}
```

## 使用规则

| 改动规模 | 模板 |
|---------|------|
| 新增模块 / ≥3 文件 / ≥100 行 | 完整模板（6 节全写） |
| 修改 1-2 文件 / 30-100 行 | 精简版：1/3/5 必写，其余按需 |
| ≤30 行 | 不用模板（执行 skill 的轻量路径，一句话说明改动） |

## 输出后的交互（第 5 目的：迭代）

方案输出后**不开始编码**，等待用户反馈：
- 用户确认 → 进入骨架阶段（foyofun-code-stub）
- 用户提出修改 → 更新方案后再次输出完整 Plan（不要只回差异）
- 用户回答了不确定点 → 把答案落进对应章节，删除已解决的不确定点
- 用户沉默超过 2 轮 → 追问一次"方案是否可行？"

## 关键原则

1. **表格优先于段落**——扫一眼就懂
2. **不猜**——每个写进方案的事实要么来自调研结论，要么列进不确定点
3. **时序表是跨层任务的灵魂**——触发/调度/呈现三列，缺一不可
4. **契约先行**——ui 和 logic 分开开发时，两边都按第 4 节的契约实现

## 与其他 Skill 的关系

| Skill | 关系 |
|-------|------|
| foyofun-code-research | 第 1/3/6 节的信息来源 |

| foyofun-code-logic / ui / integrate / refactor | 在 Plan 阶段加载本模板 |
